- metocean-stats 1.3.0: MIT, **but it requires `lmoments3`, GPL-3.0**, and `pydap`. So it is only ever run in a child process (`stats` subcommand); a test

Strict both ways: an unmapped or missing or extra column raises `VariableMappingError`. Without `height=[10]` the library returns `wind_speed_10.0m`,
`_20.0m`, ... for every height (demonstrated on the fixtures), so the height is pinned. Stored names are exactly the names `years._RAW` reads (tested).

## Library facts that matter
- It rejects `start_time`/`end_time` with a time part for the `*_sub` products (`unconverted data remains: T00:00`). **`offsim/weather/fetch.py::point_series` passes ISO times and would fail**; I did not edit it (not mine).
- It rounds every value to 0.01, has no timeouts (`xr.open_dataset(url)`), downloads a whole requested span and keeps nothing if it dies midway (its `use_cache` only keeps per-month temp files and is off by default), writes a `cache/` dir into the cwd, and prints a spinner into stdout.
- Its own retry covers only a corrupt NetCDF `KeyError`.

## Better and worse than our own fetcher
Better: official and maintained; point extraction server-side (tiny transfers) instead of a box plus Delaunay regrid; names and URLs track MET's changes;
a nearest-cell lookup that handles the rotated wave grid. Worse: no timeouts, no resume, no per-request error reporting, import cost (cartopy, metpy, ~1 s,
~4 s per child), rounding to 0.01, live file structure we cannot check offline, and an LGPL dependency. Does not do currents or gridded fields:
the legacy path stays for the visual layer.

## Resume design
- Unit = (product, month); file `pt_<product>_<YYYYMM>.nc` written to `.tmp` then `os.replace`d. 24 DJF winters = 144 units.
- On start every expected file is opened and re-validated (right product and requested point, variables, exactly the month's hourly steps, no NaN, plausible ranges). Valid: skipped. Invalid: moved to `.bad`. Stale `.tmp`: deleted.
- `manifest.json` is rewritten atomically after every unit: status, attempts, error, permanent flag, nearest cell, seconds, plus `summary` and an `errors` list in fetch_world's shape. A different point in the same directory raises `PointMismatch`.
- Each unit runs in its own subprocess, killed (process group SIGKILL) after `--unit-timeout` (600 s). SIGALRM cannot do this: netCDF4's OPeNDAP read blocks in C, so the Python handler never runs. That is the likely reason the first 30-minute stage never ended. A `.dodsrc` with `HTTP.TIMEOUT` is also written (best effort, unverified).
- Transient failures retry with backoff (15 s, 60 s); validation and mapping failures are permanent and not retried. Six consecutive failures stop the run (`stopped: consecutive_failures`); `--max-runtime-min` stops it cleanly (`stopped: deadline`). Exit code 0 only if all units are valid, else 2.
- Tests simulate the kill (KeyboardInterrupt on unit 4: 3 files and manifest survive; rerun fetches exactly 3), truncation, deletion and a leftover `.tmp`.

## The exact live command
```
pip install metocean-api
python -m offsim.worlds.metocean_api fetch --world bergen-ncs --point 3.0,60.6 --years 2000-2023 --season DJF
```
Writes `data/worlds/bergen-ncs/metocean_point/` (Dec 2000 .. Feb 2024, 144 units). Then in the scenario:
`weather: {dir: data/worlds/bergen-ncs/metocean_point, point: [3.0, 60.6], years: [2000, 2023], season: DJF}`.
- Point 3.0 E, 60.6 N: **my assumption** (open sea inside the bergen-ncs box, near Oseberg/Troll); the user may choose another over-water cell.
- Time: **unmeasured**, estimate 1 to 2.5 h (about 4 s start-up plus 10 to 60 s read per unit); the first printed `ok (N s ...)` gives N, multiply by 144.
- Resuming vs restarting: a run that finds files prints `RESUMING: 37/144 units already on disk and valid (skipped); 107 to fetch`; a fresh one prints `STARTING: 0/144 ...`. Re-run the identical command after any kill. `... metocean_api status --world bergen-ncs` shows the state without fetching.
- Inside a world fetch: `fetch_world --world bergen-ncs --out world --metocean-backend metocean-api --metocean-point 3.0,60.6 --metocean-years 2000-2023` (writes `world/metocean_point/`, adds a source and the failed units to the world manifest).
- Actions: the `fetch-world` workflow has no inputs for this and its pip line lacks metocean-api; an ephemeral runner also cannot resume unless `metocean_point/` is cached or released between runs. Needs a workflow change by whoever owns it. Easiest first live proof is the VM.

## Could not prove offline (the first live run must check these)
1. That the live monthly files have the structure the fixtures assume: waves on a rotated `rlat`/`rlon` grid with 2D `longitude`/`latitude`; wind with `height`/`y`/`x`. The fixtures follow the library's code, not a server file.
2. That the files are hourly and whole-month. If not, every unit fails loudly with the missing-hour count (no silent gaps).
3. That Dec 2000 .. Feb 2024 exist for both products on the server.
4. Seconds per unit and total time. The 600 s unit timeout is a guess.
5. `HTTP.TIMEOUT` / `HTTP.CONNECTTIMEOUT` names in `.dodsrc` (the kill is the guarantee).
6. Direction convention of `thq` in the real file; `load_years` does not interpret it.
7. That the over-water point is not a masked cell (validation raises on NaN, with the cell coordinates).
8. xarray picking netCDF4, not pydap, for the OPeNDAP URLs on the target machine.
