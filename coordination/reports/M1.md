## What was mapped
- `pyvrp` solver, classes `{"CVRP","VRPTW"}`. `Problem.tw` -> `tw_early/tw_late`, `service_s` -> `service_duration`, duration matrix
  = `dist_m / fleet speed_mps`. Objective stays total distance. Semantics are the replay's: leave the depot at t = 0, early arrival
  waits, service must START by `late`. Rounding is conservative (durations up, opens up, closes down), so a PyVRP plan is feasible in the
  continuous-time replay; the plan is re-checked in continuous time (`pyvrp_adapter.windows_violations`) before it is returned.
  An infeasible PyVRP result raises RuntimeError (never an infeasible plan).
- `pyomo` solver, classes `{"CVRP","VRPTW"}`: `vrptw_exact` (MTZ load + big-M time flow on service start times, arcs that cannot meet
  windows removed, tight per-arc big-M), HiGHS, same `max_clients = 12` refusal, `Plan.bound` and `status`. Continuous times, so exact <= PyVRP
  objective. It is the gate 1b certifier (`certify: {solver: pyomo}`): tested on the template, gate passes, status optimal.
  The model lives in `pyomo_solver.py`, not in `skills/opt-model/scripts/models.py` (not in my ownership list).
- `ampl`: `offsim/solve/ampl/vrptw.mod` (twin of the Pyomo model), `write_dat` writes `tt, svc, early, late` for VRPTW, the solver picks
  `vrptw.mod` from `Problem.cls`, `check_plan` adds `windows_ok`, `problem_from_scenario` reads `tw`/`service_s`, CLI picks the model.
  NOT solved here (no AMPL binary): the model is checked by text only (declared blocks, balanced brackets, mod params == dat params,
  the existing MCP text screen is not run on it) and the solve path is exercised with a fake AMPL session. First real solve: Actions `solve` workflow.
- `offsim/papers/_templates/vrptw/scenario.yaml` (5 stops, 2 vessels, `world: none`, `solver: pyvrp`, `engine: replay`, commented `certify:`).
  `offsim run` on it: gates 0, 1, 2, 3 pass, status "not comparable (no reported KPIs)", waits present.
- `docs/ENGINES.md`: solver table (the pyvrp row already claimed VRPTW before; now true) and a VRPTW row in Choosing.

## Still Unsupported (both solvers, one shared check `check_vrptw_features`)
- release times (`extra.release|release_s|release_times`): the replay does not hold vehicles for them.
- a window on the depot (node 0): the replay has none. Window with earliest > latest, or on a node outside 1..n-1.
- time windows with `cls` lacking `VRPTW` (they would be dropped silently), any other class in `cls`.
- more than one fleet entry (vehicle types); fractional demand/capacity/count (pyvrp); a stop whose demand exceeds capacity.
- pyomo: more than 12 clients.

## Open risks / disagreements
1. Replay engine quirk (not mine to edit): `offsim/sim/replay.py` logs `tw_late` when service ENDS after `late`; every solver here (and the
   standard VRPTW) requires service to START by `late`. With `service_s > 0` a feasible plan can log `tw_late`. Gate 2 and 3 do not look at
   `tw_late`, so runs pass; a narrator must not claim "no late stops" from that event. Fix belongs to the engine owner (check at service start).
2. Gate 1 in `pipeline.py` checks coverage and capacity only, not windows; the solvers re-check windows themselves and tests prove it, but
   gate 1 would not catch a window-violating plan from a third-party solver. Suggest a `windows_violations` call there (pipeline owner).
3. `gap list` is not on main yet; the "after" figure comes from the W6 branch code, not from main.
4. PyVRP can emit PenaltyBoundWarning when windows are infeasible; it is caught as RuntimeError, the warning is only noise.
5. `vrptw.mod` unsolved until the Actions `solve` workflow runs it (needs a VRPTW scenario passed to `ampl_adapter --scenario`).
